### 2.2 Gdzie co biegnie

- Testy jednostkowe, `eval e3` bez `--live` i `eval e3 --live --cache-only`: bez sieci i bez klucza (embeddingi referencyjne z `data/embeddings/cache`, checkpointer w pamięci).
- `eval e3 --live`: lokalnie albo w compose; wymaga `GOOGLE_API_KEY`; cache LLM-a w `paths.llm_cache_dir`. Wyszukiwanie dla D7 domyślnie w pamięci (model fastembed z configu), opcjonalnie `--backend pgvector`.
- `api` w compose: `PostgresSaver` (`workflow.checkpointer: postgres`), indeks `kovalo_ctx`, bez cache LLM-a (ADR-0008 pkt 6).

### 4.2 `kovalo.config`: zmiany

```python
class WorkflowConfig(_Section):
    checkpointer: Literal["postgres", "memory"] = "postgres"
    max_message_chars: int = Field(default=4000, ge=1)

class ServicesConfig(_Section):
    ...                                   # bez zmian

class PolicyBand(_Section):
    up_to: Decimal                        # było int; wartości z YAML bez zmian (5, 12, 20, 100)
    roles: list[str] = Field(min_length=1)

class PolicyException(_Section):
    cap: Decimal                          # było int
    roles: list[str] = Field(min_length=1)

class PolicyConfig(_Section):
    version: str
    bands: list[PolicyBand] = Field(min_length=1)
    exceptions: dict[str, PolicyException]
    margin_floor: Decimal                 # było int
    floor_role: str = Field(min_length=1)

    @model_validator(mode="after")
    def _check(self) -> PolicyConfig:
        """- up_to ściśle rosnące, ostatni przedział up_to == 100 (każdy rabat 0–100 ma przedział);
        - roles każdego wyjątku równe roles dokładnie jednego przedziału (ranga = jego indeks);
        - nazwy wyjątków ⊆ {'clearance', 'strategic_account', 'competitor_offer'} (pola DiscountRequest);
        - cap w (0, 100]. Błąd → ValueError (ConfigError przy load_settings) z nazwą klucza."""

    def band_rank(self, roles: Sequence[str]) -> int:
        """Indeks przedziału o dokładnie tych rolach (kolejność ma znaczenie); brak → ValueError."""

class Settings(BaseSettings):
    ...
    workflow: WorkflowConfig = WorkflowConfig()
```

`Decimal` z YAML: pydantic zamienia `5` na `Decimal('5')`; test porównuje `settings.policy` z sekcją kursu po `float()`. `ModelPurpose` ma już `"understand"`, więc `llm.purposes.understand` (np. `thinking_level`) działa bez zmian w kodzie.

Węzły (każdy zwraca słownik zmian; `messages` to lista nowych wiadomości):

| Węzeł | Zachowanie |
|---|---|
| `understand` | `u = understand_turn(messages[:-1], messages[-1].content, deps.understand_model, system_prompt=deps.understand_prompt)` → `{turn, decision: None, record: None, error: u.call.error, calls: [u.call]}`. Jedyny węzeł z LLM-em przed pauzami; nie ustawia statusu. |
| `answer_documents` | `rec = deps.document_answerer(turn.standalone)`; wyjątek (np. `IndexUnavailableError`) → `status 'error'`, `error`, odpowiedź z `document_reply` dla błędu, `record None`. Inaczej `record = rec.model_dump(mode='json')`, `(text, status) = document_reply(rec)`, `calls += [LlmCall('answer', rec.answered_by, rec.usage, rec.seconds, rec.error)]`. Nie zmienia `request` ani `approvals`. |
| `answer_policy` | `turn.discount_pct is None` → `MISSING_DISCOUNT`, `status 'answered'`, `decision None`. Inaczej tymczasowy `DiscountRequest` z pól `Turn` (flagi `None` → `False`) → `required_approvers` → `{decision, status 'answered', messages: [policy_answer]}`; `ValueError` → `status 'error'`, `error`, odpowiedź z komunikatem. **Nigdy** nie zapisuje `request` ani `approvals`. |
| `reply_other` | `kind 'other'` → `OTHER_REPLY`, `'answered'`; `kind 'error'` → `ERROR_REPLY`, `'error'` (`error` z `understand`). Bez wyszukiwania i bez LLM-a. |
| `update_request` | `new = update_request(state.request, turn)`, potem `d = required_approvers(new, policy)` (świeże role; `decision` z poprzedniej tury jest wyczyszczone). `ValueError` z któregoś → `{status 'error', error, messages: [komunikat]}`, wniosek i akceptacje bez zmian. Inaczej cykl życia w jednym miejscu: `keep = current is not None and new == current and all(approvals.get(r) == 'approved' for r in d.approvers)`; `approvals = approvals if keep else {}`; `status = 'pending_clarification'` gdy `new.margin_after_pct is None and not new.clearance`, inaczej `'pending_approval'`. Bez odpowiedzi (`messages` puste). |
| `clarify` | `answer = interrupt({"type": "clarification", "field": "margin_after_pct", "question": CLARIFY_QUESTION})`. Nic przed `interrupt` poza odczytem stanu. `'cancel'` → `{status 'cancelled', messages: [CANCELLED_REPLY]}`; liczba (`int`/`float`, nie `bool`, skończona, w [-100, 100]) → `{request: request.model_copy(update={'margin_after_pct': float(answer)}), status 'pending_approval', messages: [HumanMessage(margin_message(answer))]}` (ta sama wersja: to brakująca informacja, nie zmiana); cokolwiek innego → `{}` (pytamy ponownie). |
| `decide` | `d = required_approvers(request, policy)`; `ValueError` → `error`. Wszystkie role z `d.approvers` mają `'approved'` w `approvals` → `{decision d, status 'approved', messages: [already_approved_reply]}`; inaczej `{decision d, status 'pending_approval', messages: [decision_reply]}`. |
| `approve` | `role` = pierwsza rola z `decision.approvers`, której nie ma w `approvals`; `answer = interrupt({"type": "approval", "role": role, "revision": request.revision, "approvers": list(decision.approvers), "request": request.model_dump()})`. `'approved'` → `approvals[role] = 'approved'`; komplet → `{status 'approved', messages: [approved_reply]}`, inaczej tylko `approvals`. `'rejected'` → `approvals[role] = 'rejected'`, `status 'rejected'`, `rejected_reply`. `'cancel'` → `status 'cancelled'`, `CANCELLED_REPLY`. Inna wartość → `{}` (ta sama rola pytana ponownie). |

Zasady LangGraph (ADR-0009): jedno `interrupt()` na wywołanie węzła, bez `try/except` wokół niego, pętle walidacji przez krawędzie warunkowe, nic przed `interrupt()` nie wywołuje modelu ani skutków zewnętrznych. Status `approved` zawsze oznacza, że **każda** wymagana rola ma dokładnie `'approved'` (lekcja z CONCEPTS kursu).

- **`ThreadStuckError`** (P6): wyjątek spoza `Exception` albo nieobsłużony wyjątek w węźle innym niż `understand`/`answer_documents` przerywa `invoke`, a checkpoint zostaje z `next` bez pauzy. Kolejne `send_message` i `resume` w tym wątku → `ThreadStuckError` (API: 409 `thread_stuck`). Odblokowanie wątku poza F3.
- **`TurnResult.usage`** (P7) tylko w `send_message`; `resume` nie wywołuje modelu, więc `usage = None` (bez podwójnego liczenia tokenów w F6).
- **`get_values(thread_id) -> dict`** (P8, NASZE): surowe wartości stanu (`turn`, `record`, `calls`, …) dla drivera E3; API jej nie wystawia.
- **`PendingPause.key`** (P9): rola albo pole, obok `ref`. Dla doprecyzowania `revision` i `summary` są `None` (ładunek pauzy kursu ich nie ma), więc `pause_ref` z UI zawsze pasuje do `pending.ref`.

## 8. API (FR-6.1, ADR-0010)

### 8.1 Endpointy

| Metoda | Ścieżka | Wejście | 200/201 | Błędy |
|---|---|---|---|---|
| POST | `/threads` | – | 201 `ThreadCreated {thread_id}` (UUID4) | – |
| POST | `/threads/{thread_id}/messages` | `MessageIn {text}` | `TurnResult` | 409 `thread_paused` (z `pending`), 409 `thread_busy`, 409 `thread_stuck`, 422, 503 `copilot_unavailable` |
| POST | `/threads/{thread_id}/resume` | `ResumeIn {value?, text?, pause_ref?}` | `TurnResult` | 409 `not_paused`, 409 `stale_pause` (z `pending`), 409 `thread_busy`, 422 (oba albo żadne z `value`/`text`), 503 |
| GET | `/threads/{thread_id}` | – | `ThreadState` (wątek bez checkpointu: `status: null`) | 503 |
| GET | `/health` | – | bez zmian (F0) | – |

`thread_id` w ścieżce: UUID (inaczej 422). Wszystkie błędy mają ciało `ApiError {error: str, detail: str, pending: PendingPause | None}`; `detail` po polsku (np. „Wątek czeka na odpowiedź: Dyrektor handlowy. Odpowiedz na pauzę albo ją anuluj.”). Wyjątek nieoczekiwany → 500 `internal_error` bez szczegółów w ciele (szczegóły w logu).

Doprecyzowanie (P14): ciało `ApiError` ma też walidacja żądania: `RequestValidationError` (zły UUID, `value` i `text` razem albo żadne, pusty tekst, `value` spoza listy) → 422 `invalid_request` z opisem po polsku; `ValueError` z serwisu (pusta albo za długa wiadomość) → 422 `invalid_request`. Router mapuje błędy serwisu na wewnętrzny `ApiProblem` (handler w `main.py`); `thread_stuck` ma w `detail` wskazówkę „zacznij nową rozmowę”. Ślad wyjątku 500 tylko w logu `kovalo.api`.

### 9.3 `ui/app.py`

- `on_chat_start`: `CopilotApiClient(settings.services.api_url, timeout_s=settings.services.ui_api_timeout_s)` w `cl.user_session`, `thread_id = await client.create_thread()`, `pending = None`, powitanie (co umie copilot; o symulacji akceptacji mówią same komunikaty pauzy i statusu).
- `on_message`: `pending` w sesji → `client.resume(thread_id, text=message.content, pause_ref=pending.ref)`; inaczej `client.send_message(...)`. Wynik → `render_turn` → `cl.Message(content, actions=[cl.Action(name="resume", payload={"value": a.value, "pause_ref": a.pause_ref}, label=a.label)], elements=[cl.Text(name=s.name, content=s.content, display="side")])`. Nowe `pending` w sesji.
- `@cl.action_callback("resume")`: `client.resume(thread_id, value=payload["value"], pause_ref=payload["pause_ref"])`, usunięcie akcji z wiadomości z pauzą (żeby nie kliknąć drugi raz), render jak wyżej. `409 stale_pause` → „Ta decyzja jest nieaktualna”, bez zmiany stanu.
- `ApiCallError` → `render_error`; sesja zostaje (wątek po stronie api się nie zmienia).
- `409 thread_paused` przy `send_message` (np. `pending` w sesji się rozjechał) → odśwież `pending` z `get_thread` i pokaż pauzę ponownie.

Wpis marży i słowa „zatwierdź / odrzuć / anuluj” w polu czatu działają w pauzie (jak `chat.py` kursu), bo tekst idzie do `/resume` jako `text`.

Doprecyzowania (P16): `ui/client.py` ma też `pause_ref(pending)` (ten sam kształt co `PendingPause.ref`), `render.py` ma `render_pending` (także po `GET /threads/{id}`). Przyciski z poprzedniej pauzy znikają przez `cl.Message.remove_actions()` przy każdej kolejnej turze; `stale_pause` w callbacku → `action.remove()` i „Ta decyzja jest nieaktualna”, bez zmiany stanu; `thread_paused`/`stale_pause` przy wiadomości z czatu → odświeżenie pauzy z `get_thread`. Gdy `api` nie działa przy starcie czatu, wątek zakłada pierwsza wiadomość. Nazwy źródeł (`chunk_id`) są dopisane do treści („Fragmenty: …”), żeby Chainlit podlinkował panele `cl.Text(display="side")`.

### 10.6 `kovalo eval e3`

```
kovalo eval e3 [--live] [--ids LIST] [--no-cache | --cache-only] [--backend memory|pgvector] [--plan] [--out DIR]
```

| Opcja | Znaczenie |
|---|---|
| (brak) | tylko odtworzenie, zero wywołań LLM-a |
| `--live` | odtworzenie + przebieg z modelem z configu |
| `--ids` | np. `D2,D7`; nieznane id → kod 2 |
| `--no-cache` | bez cache LLM-a; domyślnie `JsonFileLlmCache(paths.llm_cache_dir, mode='read_write')` |
| `--cache-only` | `mode='strict'` + `offline=True`: zero wywołań sieciowych, bez klucza; brak wpisu → tura `error` z `LlmCacheMiss` |
| `--backend pgvector` | wyszukiwanie dla pytań o dokumenty w `kovalo_ctx` (wymaga Postgresa i `make ingest`) |
| `--plan` | wypisuje plan wywołań (`understand 13, odpowiedzi 1, razem 14`) i kończy (kod 0) |
| `--out DIR` | domyślnie `reports/mp3` |

| Kod | Sytuacja |
|---|---|
| 0 | raporty zapisane, odtworzenie 100% |
| 2 | `ConfigError` (w tym brak klucza przy `--live` bez `--cache-only`: odtworzenie zapisane), nieznane id, `--no-cache` z `--cache-only` |
| 3 | `--live` i każda tura na żywo zakończona błędem (`E3AllErrorsError`): raporty zapisane |
| 4 | odtworzenie < 100% na którymś etapie (błąd workflow, nie modelu): raporty zapisane |
| 5 | `CorpusError` |
| 6 | `--backend pgvector` i Postgres niedostępny |

Wyjście: linia planu, linia odtworzenia (`odtworzenie: kierowanie 13/13, pola 11/11, wniosek 8/8, zatwierdzający 11/11, pauzy 13/13, status 13/13, błędy 0`), linia przebiegu na żywo (te same etapy + `wywołania 14, z cache 0, modele: gemini-…: 14`), ścieżki raportów. `eval_command` kieruje `e3` do `eval_e3(settings, *, args, out, err) -> int`; nieznany etap → kod 2 „Etap eN jeszcze nie istnieje (FN).” (P13), np. „Etap e4 jeszcze nie istnieje (F4).”.

Doprecyzowania (P21): `--live` i `ConfigError` przy budowie modeli (np. brak klucza) → zapis samego odtworzenia (drugie `run_e3` bez `--live`) i kod 2. Kolejność kodów: 2, potem 4 (odtworzenie < 100%), potem 3. `review.yaml`: etykiety `ours-replay`, `ours-live`, id `<D>-t<n>` sprawdzane wobec pełnego zestawu dialogów (błąd → kod 2 przed planem). ## 11. Budżet wywołań LLM-a (darmowy tier)

Model główny `gemini-3.5-flash-lite` (dokładny dzienny limit nieznany; w F2 ok. 36 zapytań bez 429), fallback `gemini-3.6-flash` (20 zapytań/dzień, [ADR-0006](../adr/0006-config-and-llm-factory.md)). Każde wywołanie `understand` to jeden `Turn`; odpowiedź RAG jedna na pytanie o dokumenty. Graf nie wywołuje modelu przy wznowieniu (test: `ScriptedUnderstanding` wyczerpana → `AssertionError`).

| Uruchomienie | `understand` | odpowiedź RAG | Razem (górna granica) |
|---|---|---|---|
| `uv run pytest` (unit, architektura), `-m integration` | 0 | 0 | **0** |
| `kovalo eval e3` (odtworzenie) | 0 | 0 | **0** |
| `kovalo eval e3 --live` (8 dialogów, 13 tur) | 13 | 1 (D7) | **14** (kurs: tyle samo, 1,65 centa) |
| fallback w najgorszym razie (każde wywołanie Flash-Lite kończy się 429/5xx) | +13 | +1 | +14 z limitu Flash (≤ 20/dzień) |
| powtórka `--live` z cache / `--live --cache-only` | 0 | 0 | **0** (bez klucza) |
| `--live --ids D2` / `--ids D7` | 2 / 2 | 0 / 1 | 2 / 3 |
| `pytest -m live tests/live/test_e3_live.py` | 1 | 0 | **1** (bez cache) |
| przeklikanie D2 w UI (A7 lokalnie, D2 w compose; `api` bez cache) | 2 na przejście | 0 | 2 na przejście |
| **Zamknięcie F3** (A9 + powtórka z cache + T2 + D2 w UI dwa razy) | 13 + 0 + 1 + 4 | 1 | **≈ 19** |

- Gdy przebieg na żywo zatrzyma się na limicie, ponowne uruchomienie powtarza tylko brakujące wywołania (cache zapisuje udane odpowiedzi, wyjątki dostawcy nie trafiają do cache). Klucz cache zależy od historii rozmowy, a historia jest deterministyczna, dopóki wcześniejsze odpowiedzi przychodzą z cache.
- Czas: limiter 0,25 zapytania/s → co najmniej 56 s dla 14 wywołań.
- Plan (`plan_llm_calls`) wypisujemy przed pierwszym wywołaniem; `--plan` kończy program po planie.
