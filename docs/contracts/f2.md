Ten dokument zamienia F2 z [07-roadmap.md](../07-roadmap.md) na zadania z kontraktami. 4. `make ingest` buduje dwie tabele: `kovalo_mp1` (47 wierszy) i `kovalo_ctx` (87 wierszy); drugi przebieg bierze wszystkie embeddingi z cache.
5. `uv run pytest` (unit + architektura) zielone w CI; `-m integration` zielone przy działającym compose; `-m live` dla E2 to dokładnie 2 wywołania Gemini.

### 2.1 Polecenia

| Polecenie | Gdzie | Co robi |
|---|---|---|
| `kovalo ingest [--chunks mp1\|ctx\|all]` | `make ingest`; lokalnie `make ingest-local` | korpus → chunki (oba warianty domyślnie) → embeddingi (cache) → podmiana `kovalo_mp1` i `kovalo_ctx` |
| `kovalo eval e2 [opcje]` | `make eval STAGE=e2 ARGS="..."`; lokalnie `make eval-local STAGE=e2 ARGS="..."` | ewaluacja E2, raporty w `reports/mp2/` (§8.7) |

### 2.2 Gdzie co biegnie

- `ingest` i `eval e2` bez `--with-llm`: w compose albo lokalnie; bez klucza i bez sieci (model fastembed w obrazie, cache kursu w `data/`).
- `eval e2 --with-llm`: lokalnie (`make eval-local`) albo w compose; wymaga `GOOGLE_API_KEY`. Cache LLM-a w `paths.llm_cache_dir` (w compose wolumen `llm-cache`, §10.1), więc kolejne uruchomienia nie zużywają limitu.

### 2.3 Zasady zależności (dopisać do `tests/architecture/test_dependencies.py`)

Obowiązują wszystkie zasady z [f0.md §2.3](f0.md) i [f1.md §2.3](f1.md). Nowe:
- `rank_bm25` importuje tylko `kovalo/knowledge/lexical.py`.
- `langchain_text_splitters` importuje tylko `kovalo/knowledge/chunking.py`.
- `langchain_community` nie importuje żaden moduł (ADR-0007; ADR-0008: BM25 i fuzja bez `BM25Retriever`/`EnsembleRetriever`). `langchain_classic.retrievers` też nie.
- `knowledge/` nie importuje `kovalo.rag` ani `kovalo.llm` (warstwa niżej; jak w F1).
- **Generacja RAG żyje w `rag/`.** `rag/` może importować `langchain_core`, `kovalo.config`, `kovalo.knowledge`. `kovalo.llm` importuje **tylko** `rag/factory.py`; `answer.py` dostaje model przez parametr (testy podają atrapę). `rag/` nie importuje `kovalo.eval`, `kovalo.cli`, `kovalo.api`, `kovalo.ui`, `kovalo.workflow`, `kovalo.agents`, `kovalo.tools`, `kovalo.mcp_*`, `kovalo.cost`.
- `eval/` może importować `kovalo.rag`, `kovalo.knowledge`, `kovalo.cost`, `kovalo.llm`; nadal nie importuje `cli`, `api`, `ui`.
- `llm.py` nie importuje `kovalo.eval` (cache LLM-a dostaje przez parametr typu `langchain_core.caches.BaseCache`).
- `ui/` nie importuje `kovalo.rag` (już w F0).
- Literał `gpt-` jest nadal zabroniony w `src/`: nazwę modelu referencyjnego w raporcie E2 bierzemy z `settings.reference_llm.model`, nie ze stałej (§8.5).

### 5.1 `knowledge/chunking.py`: chunki z kontekstem (FR-2.1, krok 1 kursu)

```python
def make_ctx_chunk_id(doc_id: str, index: int) -> str:
    """'CON-101', 3 → 'CON-101#ctx003'. index < 0 albo > 999 → ValueError (jak make_chunk_id)."""

def build_contextual_chunks(docs: Sequence[Document], chunking: ChunkingConfig) -> list[Document]:
    """Dla każdego dokumentu (kolejność zachowana):
    1. MarkdownHeaderTextSplitter(list(HEADERS_TO_SPLIT_ON), strip_headers=False).split_text(page_content);
    2. RecursiveCharacterTextSplitter(chunk_size, chunk_overlap, separators).split_documents(części);
    3. section = część.metadata.get('h2', ''); nagłówek = title, gdy section == '', inaczej f'{title} > {section}';
       page_content = f'{nagłówek}\\n\\n{tekst części}';

       i = 0, 1, … w obrębie dokumentu. Klucze splittera ('h1', 'h2') NIE trafiają do metadanych.
    Dokument bez metadata['doc_id'] albo metadata['title'] → ValueError."""

def build_chunks(docs: Sequence[Document], chunking: ChunkingConfig, variant: ChunkVariant) -> list[Document]:
    """'mp1' → chunk_documents, 'ctx' → build_contextual_chunks."""
```

`title` pochodzi z `metadata["title"]` (katalog), nie z nagłówka `#` w tekście. `chunk_index` jest potrzebny jako kolumna metadanych `PGVectorStore` (F1 §5.6). `chunk_stats` z F1 działa bez zmian dla obu wariantów.

```python
        """vec = search(store, question, params.fetch_k); lex = lexical.search(question, params.fetch_k);
        rrf_fuse([vec, lex], weights=[w.vector, w.bm25], c=params.rrf_c)[:k]. Wynik = wynik RRF (nie cosine).
        k > fetch_k → ValueError."""

def rrf_fuse(rankings: Sequence[Sequence[ScoredChunk]], *, weights: Sequence[float], c: int) -> list[ScoredChunk]:
    """Ważona Reciprocal Rank Fusion po metadata['chunk_id']: wynik = Σ w_i / (c + pozycja_i), pozycje od 1.
    Chunk z kilku list występuje raz (Document z pierwszej listy, w której wystąpił). Sortowanie malejąco po wyniku,
    remis → rosnąco po chunk_id. len(rankings) != len(weights), waga ujemna albo wszystkie zerowe → ValueError.
    Wyniki wejściowe (cosine, BM25) są ignorowane: liczą się tylko pozycje."""

def build_retriever(chunks: Sequence[Document], store: VectorStore, *, mode: RetrievalMode,
                    hybrid: HybridConfig) -> Retriever:
    """'vector' → VectorRetriever(store); 'hybrid' → HybridRetriever(store, BM25Index(chunks, hybrid.bm25), hybrid).
    chunks to te same chunki co w store (BM25 trzyma je w pamięci)."""

def open_retriever(settings: Settings, embeddings: Embeddings, *, variant: ChunkVariant = "ctx",
                   mode: RetrievalMode | None = None) -> Retriever:
    """Wyszukiwanie produkcyjne (Postgres). table = db.vector_collection ('ctx') albo db.vector_collection_mp1 ('mp1');
    meta = check_index(settings, table, …) (F1 §5.6); store = open_store(...);
    chunks = build_chunks(load_corpus(settings), settings.chunking, variant);
    len(chunks) != meta.n_chunks → IndexMismatchError('… korpus i indeks się różnią. Uruchom make ingest.');
    mode=None → settings.retrieval.mode. Import kovalo.knowledge.pgvector leniwie."""
```

Uzasadnienie wyboru: [ADR-0008](../adr/0008-rag-hybrid-e2.md) pkt 2. Indeks BM25 powstaje z korpusu przy starcie procesu (87 chunków, milisekundy), a nie z wierszy Postgresa; zgodność pilnuje porównanie z `kovalo_index_meta.n_chunks`.

`cache` działa na poziomie `BaseChatModel._generate_with_cache` (`langchain-core` 1.7): trafienie w cache pomija rate limiter i wywołanie sieciowe, a zwrócony `AIMessage` ma oryginalne `usage_metadata` (z `total_cost: 0`). Klucz cache to `(prompt, llm_string)`, a `llm_string` zawiera model, parametry i schemat odpowiedzi; test w §11 sprawdza, że jest stabilny między instancjami i nie zawiera klucza API.

Przebieg `run_e2`:
1. Korpus raz; chunki `mp1` i `ctx` raz; `chunks_not_in_course_cache` przez `missing_from_course_cache` (F1).
2. **Poziomy 1–2 bez LLM-a, zawsze:** dla każdej strony embeddingów i każdego z trzech wariantów: retriever (`build_retriever` na `InMemoryVectorStore`; backend `pgvector`: `open_retriever` dla strony `ours`), dla 10 pytań z odpowiedzią: top-k, hit@1, hit@3, `all_required_found`, `evidence_phrase_coverage`, tokeny promptu. Argument `variants` nie zawęża tej części.
3. **Poziomy 3–4 tylko z `with_llm`:** dla wariantów z `variants` na stronie `llm_side`, dla pytań (`ids` albo wszystkie 12): `answer_question` → `score_record` → `judge_record` (gdy `judge`) → `QuestionRow`; `summarise`. Modele: `answer_model or get_structured_model(Answer, 'answer', cache=cache)`, `judge_model or get_structured_model(Verdict, 'judge', cache=cache)`; zbudowane raz przed pętlą (brak klucza → `ConfigError` przed pierwszym wywołaniem).
4. Liczniki `LlmCalls` z różnicy `cache.hits`/`misses` wokół każdego wywołania; bez cache wszystkie wywołania liczą się jako sieciowe.
5. Pytania i warianty idą sekwencyjnie (rate limiter i tak serializuje wywołania; brak równoległości upraszcza liczniki).

`ids` nieznane w zestawie → `ConfigError` z listą znanych. Gdy w wariancie z LLM-em każdy rekord odpowiedzi to błąd, `run_e2` zgłasza `E2AllErrorsError(report)` po zbudowaniu raportu (CLI zapisuje raporty i kończy kodem 3; odpowiednik `SystemExit` z kursu).

**Reguła rekomendacji trybu (`recommend_mode`, deterministyczna, strona `ours`):** `hybrid`, gdy hybryda nie jest gorsza od `ctx` w żadnej z miar: hit@1, hit@3, komplet dowodów, a przy wynikach LLM-a obu wariantów także `answered`, `key_facts_complete`, `judge_correct`; i jest lepsza w co najmniej jednej. W przeciwnym razie `vector`. Brak strony `ours` → `None`. Rekomendacja nie zmienia configu: decyzję o `retrieval.mode` podejmuje właściciel projektu (pytanie U2), a R1 zapisuje ją w ADR-0008.

### 14.3 Zadanie P1: komentarze z przeglądu ręcznego w `review.yaml`

**Decyzja.** Komentarze z przeglądu (T2 i kolejne) żyją w pliku wejściowym `<out>/review.yaml` (dla E2: `reports/mp2/review.yaml`, commitowany), a generator wstawia je do sekcji „Rozbieżności przejrzane ręcznie”. Wygenerowanego Markdownu nie edytujemy ręcznie. Klucz wpisu: etykieta wariantu `<strona>-<wariant>` (jak w nazwach `answers.<strona>-<wariant>.json`) + id pytania. YAML, bo komentarze są wielowierszowe, a `pyyaml` już jest w zależnościach. Moduł jest ogólny (`eval/review.py`), żeby E3–E5 użyły go z własnymi etykietami.

**Format** (`version: 1`, nieznane klucze → błąd):

```yaml
version: 1
reviewed_on: 2026-11-02
intro: |                        # opcjonalny akapit pod nagłówkiem sekcji (Markdown)
  Przegląd T2 na podstawie answers.ours-*.json i live_report.ours-*.json. …
items:
  - variants: [ours-ctx]        # ≥ 1 etykieta; para (etykieta, id) najwyżej raz w pliku
    id: M04
    answer_digest: {ours-ctx: 3f2a9c0d1b7e}   # opcjonalnie: odpowiedź, której dotyczy komentarz
    comment: |                  # niepusty, Markdown, wiele wierszy
      Odmowa uczciwa, ocena trafna; to realne pudło wyszukiwania …
  - variants: [ours-ctx, ours-hybrid]
    id: M09
    comment: |
      Odpowiedzi przesadzają: …
notes:                          # opcjonalne punkty na końcu sekcji
  - Pozostałe uzasadnienia sędziego (M01–M03, M05, M06, M08, M10, oba warianty): …
  - Odmowy M11, M12: poprawne w obu wariantach.
```

**Sygnatury** (`src/kovalo/eval/review.py`, bez LangChaina):

```python
REVIEW_FILE = "review.yaml"

class ReviewItem(BaseModel):                     # model_config = ConfigDict(extra="forbid")
    variants: list[str] = Field(min_length=1)    # każda: ^[a-z0-9]+-[a-z0-9]+$
    id: str = Field(min_length=1)
    comment: str = Field(min_length=1)           # po strip()
    answer_digest: dict[str, str] = {}           # klucze ⊆ variants, wartości ^[0-9a-f]{12}$

class Review(BaseModel):                         # extra="forbid"
    version: Literal[1]
    reviewed_on: date
    intro: str = ""
    items: list[ReviewItem] = []
    notes: list[str] = []
    # walidator: para (etykieta, id) najwyżej raz w całym pliku
    def find(self, variant: str, id: str) -> ReviewItem | None: ...

def load_review(path: Path) -> Review | None:
    """Brak pliku → None. yaml.safe_load + Review.model_validate; błąd YAML albo schematu →
    ConfigError(f'{path}: …') z lokalizacją pola (np. 'items.2.comment')."""

def check_review_keys(review: Review, *, variants: Collection[str], ids: Collection[str]) -> None:
    """Etykieta spoza `variants` albo id spoza `ids` → ConfigError z listą znanych (literówka w kluczu
    nie może po cichu zgubić komentarza)."""

def answer_digest(answer: str | None, error: str | None = None) -> str:
    """sha256((answer if answer is not None else error or '').encode('utf-8')).hexdigest()[:12]."""
```

```python
def render_markdown(report: E2Report, review: Review | None = None) -> str: ...
```

Zasady sekcji „Rozbieżności przejrzane ręcznie” z `review`:
1. Pod nagłówkiem `intro` (jeśli jest) i linia „Komentarze: review.yaml, przegląd <reviewed_on>”.
2. Lista automatyczna jak dziś (§8.8). Etykieta pozycji `f"{side}-{variant}"`; w wierszu pozycji z LLM-em dopisek „· odpowiedź #<answer_digest>”, żeby recenzent mógł go skopiować. „Komentarz:” z `review.find(etykieta, id)` (wiele wierszy wciętych pod punktem), a bez wpisu „(do uzupełnienia w T2)”.
3. Gdy wpis ma `answer_digest[etykieta]` różny od bieżącego: dodatkowa linia „Uwaga: komentarz dotyczy innej odpowiedzi (#stary, teraz #nowy); przejrzyj ponownie.” (zmiana modelu, promptu albo wyczyszczony cache).
4. Wpisy, które nie pasują do żadnej pozycji automatycznej, ale mają wiersz w raporcie (np. M09 i M07 hybrid po poprawce): po liście, jako „<etykiety>, <id> (dodane w przeglądzie ręcznym)” z bieżącymi danymi każdego wariantu (wynik, pokrycie, sędzia, uzasadnienie sędziego) i komentarzem.
5. Wpisy bez wiersza w raporcie (wariant nieuruchomiony, `--ids`): na końcu, „Komentarze bez pozycji w tym przebiegu”, z treścią. Nic nie znika po cichu.
6. `notes` jako punkty na końcu sekcji.
7. `review=None` daje dokładnie dzisiejszy wynik (istniejące testy bez zmian). Raport bez LLM-a (pozycje z `_retrieval_review_items`) używa tych samych etykiet i zasad.

CLI (`eval_e2`): zaraz po walidacji `--variants`/`--ids`, przed planem, cache i budową modeli: `review = load_review(out_dir / REVIEW_FILE)`, a jeśli jest, `check_review_keys(review, variants=[f"{s}-{v}" for s in SIDES for v in VARIANTS], ids=[q.id for q in gold])`. `ConfigError` → kod 2, zero wywołań. Potem `write_reports(..., review=review)`. Bez nowej opcji (`--out DIR` czyta `DIR/review.yaml`). `.gitignore`: dopisać `!reports/*/review.yaml`. Plik JSON raportu nie zawiera komentarzy: Markdown = f(JSON, review.yaml).

**Testy** (test-engineer, najpierw czerwone): `tests/unit/eval/test_review.py`: `test_load_review_missing_returns_none`; `test_load_review_rejects_bad_files` (zły YAML, `version: 2`, nieznany klucz, pusty `comment`, zduplikowana para, `answer_digest` z kluczem spoza `variants` → `ConfigError` z nazwą pliku); `test_check_review_keys` (nieznana etykieta, nieznane id); `test_answer_digest_stable` (ta sama treść → ten sam skrót, 12 znaków hex; `None` + błąd → skrót błędu). `tests/unit/eval/rag/test_e2_report.py`: `test_review_comment_replaces_placeholder`; `test_review_item_without_discrepancy_rendered` (wpis dla wiersza bez rozbieżności: dane bieżące + komentarz); `test_review_orphan_kept`; `test_review_stale_digest_warning`; `test_render_without_review_unchanged`; `test_render_with_review_idempotent` (dwa `write_reports` → identyczny Markdown). `tests/unit/test_cli.py`: `test_eval_e2_reads_review` (`--out tmp_path` z `review.yaml` → komentarz w Markdownie); `test_eval_e2_bad_review_exit_2` (kod 2, atrapa modelu niewywołana, `--with-llm`).

**Doprecyzowania (test-engineer i ai-engineer, przy implementacji P1).**
- Wzorce etykiety `^[a-z0-9]+-[a-z0-9]+$` i skrótu `^[0-9a-f]{12}$` są na modelu (`ReviewItem`), nie tylko w `check_review_keys`. `comment` po walidacji bez pustych wierszy na początku i końcu.
- `render_markdown` nie wywołuje `check_review_keys`: walidacja kluczy tylko w CLI (raport z `--ids` albo bez strony reference nie może się wywracać na wpisie bez wiersza; taki wpis trafia do „Komentarze bez pozycji w tym przebiegu”).
- Z `review` nagłówek pozycji automatycznej ma etykietę z myślnikiem (`- ours-ctx, M04: … · odpowiedź #…`); bez `review` zostaje dzisiejsze `- ours ctx, M04:` (zasada 7). Testy akceptują obie formy.
- „Komentarz:” to punkt `  - Komentarz: <1. wiersz>`, kolejne wiersze wcięte o 4 spacje. Linia ostrzeżenia o skrócie stoi przed komentarzem.
- Wpis bez automatycznej rozbieżności: jedna pozycja na wpis, `- <etykiety>, <id> (dodane w przeglądzie ręcznym)`, potem dla każdej etykiety `  - <etykieta>: wynik …, pokrycie …, sędzia … · odpowiedź #…` i `  - Uzasadnienie sędziego: …` (gdy jest), na końcu komentarz raz. Bez LLM-a: dane wyszukiwania (hit@1, hit@k, dowody, top-k). Etykiety wpisu obsłużone przez pozycję automatyczną nie powtarzają się tu.
- Wpisy bez wiersza: akapit „Komentarze bez pozycji w tym przebiegu:” i punkty `- <etykiety>, <id>` z komentarzem.
- `notes` jako ostatnie linie sekcji (po pustej linii).
- CLI: błąd wczytania albo kluczy → komunikat ze ścieżką `<out>/review.yaml` na stderr, kod 2, przed planem i budową modeli (także embeddingów).
- Poprawione: `test_review_item_without_discrepancy_rendered` sprawdzał `row.verdict.reason` dla M11 (poprawna odmowa, sędzia nie ocenia odmów, więc `reason` = `None`). Test sprawdza teraz uzasadnienie tylko, gdy istnieje, oraz wynik wiersza (`outcome`). M01 się nie nadaje: w atrapie każda odpowiedź ma rozbieżność.
